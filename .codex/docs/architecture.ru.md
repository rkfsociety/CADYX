# Архитектура CADYX — основа

> Перевод выполняется. Ниже переведены граница продукта, хранение, доступность проекта и блокировки. Остальные разделы архитектуры пока доступны на английском в [исходном контракте](architecture.md).

## Граница продукта

CADYX изначально спроектирован для работы ИИ-агентов: они используют версионированный API и общую Command System Core. Браузер — полноэкранный просмотрщик для чтения; агенты создают проекты и редактируют модели через Agent API, а клиенты-человеки могут использовать защищённые блокировкой маршруты Web API.

Дерево объектов находится во вкладке Geometry; просмотр файлов проекта доступен с учётом активности и блокировки агента. Браузер не обращается напрямую к геометрическому ядру и не владеет CAD-состоянием. Он показывает модель в реальном времени и одну строку с текущим действием/результатом, не выводя поток исходных команд или стенограмму.

Встроенная панель Revopoint отображает текущий кадр глубины либо сохранённый ASCII PLY только с точками из папки workspace. Сохранённые облака отрисовываются непосредственно точками через read-only-маршрут `/api/v1/scanner/point-cloud`; превью не преобразует их в треугольную сетку и не утверждает метрический масштаб.

```text
Адаптер провайдера (будущий) -> Agent Runtime -> CADYX Core -> Command System -> Document
Внешний агент --------------------------> Agent API -> CADYX Core -> Project Workspace
Браузер --------------------------------> Web API -> CADYX Core -> Project Workspace
                                                             |       Адаптер Geometry Kernel
                                                             +-> брокер событий -> SSE -> Браузер
```

Локальный прототип использует модули стандартной библиотеки Python для Core, Agent Runtime и HTTP-сервера, а интерфейс — обычные HTML/CSS/JavaScript. Текущая среда Windows x64 использует Python 3.15, нативный OCCT 8.0.1 и CPU-сборку Open3D 0.20.0 через собранные проектом мосты C ABI (`native/`, `cadyx/native_kernel.py`, `cadyx/native_scan.py`), независимые от ABI расширений Python.

Читатель STEP OCCT подключён через `TKDESTEP`; остальные runtime-DLL закреплены хешами в `scripts/occt-runtime-lock.json` и устанавливаются через `scripts/setup-runtime.ps1`. Open3D обрабатывает очистку облаков точек PLY, реконструкцию поверхностей screened Poisson и упрощение сеток. Обработчик ограничивает вычисления четырьмя потоками и 100000 точками. Для чтения PLY и предварительной обработки используются тензорные API; затем облако преобразуется в legacy API для screened Poisson, поскольку тензорного аналога нет. Очистка и упрощение треугольных сеток используют legacy API сеток Open3D.

Браузер получает от Core сетки тел и примитивы эскизов в именованных рабочих плоскостях XY/XZ/YZ и CUSTOM/FACE через тот же ортографический canvas с осью Z вверх, что и для PLY из папок. Чтобы сохранять отзывчивость браузера, большие PLY для отображения дискретизируются.

Снимки активности Core и события SSE сохраняют для клиентов Agent API реальные этапы команд, твердотельных операций, камеры и нативного сканирования. Интерфейс показывает одну карточку прогресса: текущий статус, прогресс/ETA, текущее или последнее реальное действие агента, текущую/последнюю завершённую задачу и историю завершённых/ошибочных действий — новые сначала, с локальным временем завершения. Планируемые этапы и будущая очередь доступны по Agent API, но браузер их скрывает. Активность хранится в памяти процесса; отчёты dashboard сохраняются строками по проектам в runtime SQLite-базе workspace. Отчёт и глобальная ревизия работы фиксируются одной транзакцией. При первом старте без базы старое состояние dashboard в JSON импортируется.

Внешние агенты публикуют состояние dashboard через Agent API. Данные телеметрии оборудования сейчас недоступны. См. [Agent Runtime](#agent-runtime) в оригинале, [Viewport API](viewport-api.md), [контракт импорта сканов](document-model-v7.md#scan-import-and-editable-triangle-meshes), [контракт импорта STEP](document-model-v7.md#step-import-and-editable-b-reps) и [настройку среды](../../docs/operations.ru.md).

## Core и хранение

Для текущих версий проекта и документа Workspace читает и проверяет разобранный снимок напрямую, без копии для миграции. Разделяемые записями тела, элементов и истории данные B-rep хранятся один раз в скрытых файлах проекта по content hash; перед валидацией и ответом API ссылки раскрываются. Подробнее — [формат проекта](project-format-v1.ru.md).

Загрузка команд/preview использует число и байтовое смещение последней зафиксированной записи истории, не разбирая заново журнал. При сохранении добавляются только новые записи, а полная инспекция проекта проверяет зафиксированную часть журнала. Каждая команда выполняется на изолированном документе и добавляет в историю только свои записи. Уже проверенный документ повторно не валидируется на границе сохранения.

`cadyx/core.py` — граница приложения для обоих API. `ProjectWorkspace` хранит по одному версионированному `project.json` в каталоге проекта с понятным именем. Имя для новых проектов очищается для файловой системы; при совпадении добавляется числовой суффикс. Уже зарегистрированные каталоги сохраняют имена. Локальная метка `.cadyx-project-id` удерживает UUID доступным даже при повреждённом `project.json`. UUID остаётся идентификатором API и блокировки, старые каталоги, названные UUID, остаются читаемыми.

Файл проекта содержит метаданные, состояние документа, ревизию и историю команд. При загрузке явные последовательные миграции `cadyx/migrations.py` применяются к изолированной копии только если оболочка проекта или вложенный документ старше текущей версии. Актуальный снимок проверяется без миграционной копии; чтение не переписывает файлы. См. [контракт миграции](project-format-v1.ru.md#migration-contract).

Каждая принятая команда меняет изолированный документ и атомарно заменяет `project.json`; ревизия документа и успешная запись истории фиксируются вместе. Read-only-списки, инспекция документа и рендер viewport используют последний атомарно сохранённый снимок, поэтому перезагруженная страница может восстановить модель, пока агент удерживает блокировку для следующей команды. Обе конечные точки списка проектов принимают на месте каждый непосредственный каталог без символьной ссылки и записи проекта, публикуя устойчивую UUID-метку и пустой `project.json`; существующие пользовательские файлы сохраняются.

Каталог `projects/` содержит runtime-данные и игнорируется Git, кроме `.gitkeep`. Исходные сканы, сетки, CAD-файлы, изображения, измерения и референсы считаются пользовательскими данными: при обычной разработке их нельзя перезаписывать или удалять.

Agent API может загрузить STEP или PLY-файл маршрутом `POST /api/v1/agent/projects/{id}/files/{name}` (`application/octet-stream`, максимум 64 МиБ). Загрузка допускается в свободный проект, только с непосредственным именем `.step`, `.stp` или `.ply`, и не заменяет существующий файл.

`import_project_scan` обрабатывает помещённый в проект PLY в редактируемую треугольную сетку и сохраняет имя/хеш источника, чтобы последующие изменения параметров заново обрабатывали именно исходный файл. Локальный MCP-адаптер предоставляет загрузку STEP и PLY через `cadyx_upload_project_step` и `cadyx_upload_project_scan`: оба читают локальный обычный файл и передают его байты, а HTTP-хост не раскрывает произвольные пути клиента.

Для временных референсов реконструкции `DELETE /api/v1/agent/projects/{id}/files/{name}` удаляет только непосредственный STEP из свободного проекта и отказывается это делать, пока актуальный `import_step` продолжает использовать файл. MCP-команда `cadyx_remove_staged_step` удаляет референс лишь после удаления тела; исходный локальный файл не меняется.

`POST /api/v1/agent/projects/{id}/copy-files` рекурсивно копирует пользовательские файлы из другого свободного проекта, исключая метаданные и runtime-состояние `.cadyx-*`; сначала проверяются конфликты, перезапись запрещена. MCP-эквивалент — `cadyx_copy_project_files`. `POST /api/v1/agent/projects/{id}/prune-files` рекурсивно удаляет пользовательские файлы, сохраняя указанные прямые имена. Он требует свободный проект с пустым документом, сохраняет метаданные проекта и `.cadyx-*`, сообщает хеши оставшихся файлов. MCP-эквивалент — `cadyx_prune_project_files`. К файловым маршрутам применяется политика аутентификации хоста.

`POST /api/v1/agent/projects` принимает `select: false`, чтобы создать проект, не меняя выбор браузера, например, для загрузки файла, пока агент работает с другим проектом.

## Политики доступности проекта

`CadyxCore._project_availability` объединяет снимок блокировки и состояние выполняющейся операции. Сохранённая активность dashboard остаётся отдельным сигналом для интерфейса/отчётов, но не участвует в допуске команды Core. Политика доступности — единая граница Core для чтения и записи проекта, управления файлами, выбора ресурсов и деструктивных операций. Отсутствующая, занятая или неизвестная блокировка не считается свободной.

Read-only-инспекция и списки используют неблокирующий снимок lease и возвращают последний атомарно сохранённый проект, даже пока работает писатель. Новую блокировку на изменение можно получить лишь для свободного проекта без требования восстановления и без выполняющейся операции; команда всё равно должна получить допустимую блокировку владельца и ревизию. Уже принятая к исполнению с корректной блокировкой команда остаётся атомарной, даже если блокировка истечёт во время работы.

Управление файлами и разрушительные действия требуют `FREE`, отсутствия восстановления блокировки и активной операции; в противном случае сохраняются существующие ошибки `PROJECT_BUSY` или `PROJECT_LOCKED`.

Выбор workspace — подсказка процессу браузера, а не способ определить владельца или направить команду. Core проверяет только целевой проект: он должен быть `FREE`, без требования восстановления и выполняющихся операций; можно выбрать проект с незавершённым workflow, если в данный момент между командами. Разрешено переключиться с занятого текущего проекта и выбрать проект, пока у других выполняются workflows. Создание проекта с выбором не ждёт workflows остальных проектов; `select: false` сохраняет текущий выбор. Разные чаты должны явно передавать `project_id` при операциях с проектом. Только отдельная блокировка проекта предотвращает одновременное редактирование двумя сессиями.


## Блокировки на изменение

В боковой базе `.cadyx-leases.sqlite3` у каждого проекта хранится одна долговечная блокировка, общая для локальных процессов хоста, использующих один workspace. Запись содержит `project_id`, `owner_type`, `owner_id`, время получения и heartbeat, непрозрачный `lease_id` и тайм-аут, выбранный при получении. Типы владельца: `agent`, `human`, `system`; состояния включают `FREE`, `AI_LOCKED`, `HUMAN_LOCKED`, `SYSTEM_LOCKED`. Heartbeat с хоста, настроенного на иной тайм-аут, не меняет исходный срок блокировки.

Все записи документа проходят через `CadyxCore.execute_command` и требуют текущий ID блокировки с подходящим для данного API владельцем-человеком или агентом. Транзакция SQLite `BEGIN IMMEDIATE` удерживает межпроцессную блокировку ОС проекта на время проверки lease, загрузки документа, выполнения команды, проверки и атомарной замены `project.json`. Получение, heartbeat, освобождение, инспекция и восстановление используют ту же блокировку. У разных проектов отдельные базы, они остаются независимыми.

Если занятый проект не освободился за пять секунд ожидания, операция возвращает `PROJECT_BUSY` (HTTP 409). Её можно повторить; текущую команду не прерывают.

Истечение heartbeat помечает блокировку устаревшей, но не освобождает проект автоматически. Для восстановления Core получает ту же блокировку, загружает последний атомарно сохранённый проект, проверяет документ и геометрию и лишь затем удаляет просроченную запись. Команда, начатая с корректной блокировкой, может завершиться после её истечения; восстановление не пересечётся с сохранением.

При аварийном завершении процесса блокировка SQLite снимается, но зафиксированный lease сохраняется, в том числе после перезапуска сервера. После истечения срока всё равно требуется процедура восстановления. Сбой до атомарной замены оставляет прежнюю ревизию; сбой после — полный новый документ и историю. Клиент мог не получить ответ, поэтому перед повторным запуском команды после потери связи проверьте сохранённую историю.

Механизм рассчитан на взаимодействующие актуальные хосты CADYX на одной локальной машине и локальной файловой системе. Перед обновлением остановите старые хосты: прежние версии не поддерживают текущий протокол остановки агента, а самые ранние не имеют общих межпроцессных блокировок. Не удаляйте и не заменяйте базы координации или журналы при работающих хостах. Резервное копирование/перенос выполняйте при остановленных хостах; боковые файлы координации — отдельные runtime-данные, не часть переносимого `project.json`. Прямая запись сторонними процессами и сетевые файловые системы вне контракта.

Доставка SSE ограничена процессом. Лёгкий периодический опрос обновлений браузером автоматически показывает подтверждённые изменения проекта и файлов workspace, внесённые другим взаимодействующим хостом.
