# Архитектура CADYX — основа

> Перевод выполняется. Ниже переведены граница продукта, хранение, доступность проекта и блокировки. Остальные разделы архитектуры пока доступны на английском в [исходном контракте](architecture.md).

## Граница продукта

CADYX изначально спроектирован для работы ИИ-агентов: они используют версионированный API и общую Command System Core. Браузер — полноэкранный просмотрщик для чтения; агенты создают проекты и редактируют модели через Agent API, а клиенты-человеки могут использовать защищённые блокировкой маршруты Web API.

Дерево объектов находится во вкладке Geometry; просмотр файлов проекта доступен с учётом активности и блокировки агента. Браузер не обращается напрямую к геометрическому ядру и не владеет CAD-состоянием. Он показывает модель в реальном времени и одну строку с текущим действием/результатом, не выводя поток исходных команд или стенограмму.

Встроенная панель Revopoint отображает текущий кадр глубины либо сохранённый ASCII PLY только с точками из папки workspace. Сохранённые облака отрисовываются непосредственно точками через read-only-маршрут `/api/v1/scanner/point-cloud`; превью не преобразует их в треугольную сетку и не утверждает метрический масштаб.

```text
Адаптер провайдера (будущий) -> Agent Runtime -> CADYX Core -> Command System -> Document
Внешний агент --------------------------> Agent API -> CADYX Core -> Project Workspace
Браузер --------------------------------> Web API -> CADYX Core -> Project Workspace
                                                             |       Адаптер Geometry Kernel
                                                             +-> брокер событий -> SSE -> Браузер
```

Локальный прототип использует модули стандартной библиотеки Python для Core, Agent Runtime и HTTP-сервера, а интерфейс — обычные HTML/CSS/JavaScript. Текущая среда Windows x64 использует Python 3.15, нативный OCCT 8.0.1 и CPU-сборку Open3D 0.20.0 через собранные проектом мосты C ABI (`native/`, `cadyx/native_kernel.py`, `cadyx/native_scan.py`), независимые от ABI расширений Python.

Читатель STEP OCCT подключён через `TKDESTEP`; остальные runtime-DLL закреплены хешами в `scripts/occt-runtime-lock.json` и устанавливаются через `scripts/setup-runtime.ps1`. Open3D обрабатывает очистку облаков точек PLY, реконструкцию поверхностей screened Poisson и упрощение сеток. Обработчик ограничивает вычисления четырьмя потоками и 100000 точками. Для чтения PLY и предварительной обработки используются тензорные API; затем облако преобразуется в legacy API для screened Poisson, поскольку тензорного аналога нет. Очистка и упрощение треугольных сеток используют legacy API сеток Open3D.

Браузер получает от Core сетки тел и примитивы эскизов в именованных рабочих плоскостях XY/XZ/YZ и CUSTOM/FACE через тот же ортографический canvas с осью Z вверх, что и для PLY из папок. Чтобы сохранять отзывчивость браузера, большие PLY для отображения дискретизируются.

Снимки активности Core и события SSE сохраняют для клиентов Agent API реальные этапы команд, твердотельных операций, камеры и нативного сканирования. Интерфейс показывает одну карточку прогресса: текущий статус, прогресс/ETA, текущее или последнее реальное действие агента, текущую/последнюю завершённую задачу и историю завершённых/ошибочных действий — новые сначала, с локальным временем завершения. Планируемые этапы и будущая очередь доступны по Agent API, но браузер их скрывает. Активность хранится в памяти процесса; отчёты dashboard сохраняются строками по проектам в runtime SQLite-базе workspace. Отчёт и глобальная ревизия работы фиксируются одной транзакцией. При первом старте без базы старое состояние dashboard в JSON импортируется.

Внешние агенты публикуют состояние dashboard через Agent API. Данные телеметрии оборудования сейчас недоступны. См. [Agent Runtime](#agent-runtime) в оригинале, [Viewport API](viewport-api.md), [контракт импорта сканов](document-model-v7.md#scan-import-and-editable-triangle-meshes), [контракт импорта STEP](document-model-v7.md#step-import-and-editable-b-reps) и [настройку среды](../../docs/operations.ru.md).

## Core и хранение

Для текущих версий проекта и документа Workspace читает и проверяет разобранный снимок напрямую, без копии для миграции. Разделяемые записями тела, элементов и истории данные B-rep хранятся один раз в скрытых файлах проекта по content hash; перед валидацией и ответом API ссылки раскрываются. Подробнее — [формат проекта](project-format-v1.ru.md).

Загрузка команд/preview использует число и байтовое смещение последней зафиксированной записи истории, не разбирая заново журнал. При сохранении добавляются только новые записи, а полная инспекция проекта проверяет зафиксированную часть журнала. Каждая команда выполняется на изолированном документе и добавляет в историю только свои записи. Уже проверенный документ повторно не валидируется на границе сохранения.

`cadyx/core.py` — граница приложения для обоих API. `ProjectWorkspace` хранит по одному версионированному `project.json` в каталоге проекта с понятным именем. Имя для новых проектов очищается для файловой системы; при совпадении добавляется числовой суффикс. Уже зарегистрированные каталоги сохраняют имена. Локальная метка `.cadyx-project-id` удерживает UUID доступным даже при повреждённом `project.json`. UUID остаётся идентификатором API и блокировки, старые каталоги, названные UUID, остаются читаемыми.

Файл проекта содержит метаданные, состояние документа, ревизию и историю команд. При загрузке явные последовательные миграции `cadyx/migrations.py` применяются к изолированной копии только если оболочка проекта или вложенный документ старше текущей версии. Актуальный снимок проверяется без миграционной копии; чтение не переписывает файлы. См. [контракт миграции](project-format-v1.ru.md#migration-contract).

Каждая принятая команда меняет изолированный документ и атомарно заменяет `project.json`; ревизия документа и успешная запись истории фиксируются вместе. Read-only-списки, инспекция документа и рендер viewport используют последний атомарно сохранённый снимок, поэтому перезагруженная страница может восстановить модель, пока агент удерживает блокировку для следующей команды. Обе конечные точки списка проектов принимают на месте каждый непосредственный каталог без символьной ссылки и записи проекта, публикуя устойчивую UUID-метку и пустой `project.json`; существующие пользовательские файлы сохраняются.

Каталог `projects/` содержит runtime-данные и игнорируется Git, кроме `.gitkeep`. Исходные сканы, сетки, CAD-файлы, изображения, измерения и референсы считаются пользовательскими данными: при обычной разработке их нельзя перезаписывать или удалять.

Agent API может загрузить STEP или PLY-файл маршрутом `POST /api/v1/agent/projects/{id}/files/{name}` (`application/octet-stream`, максимум 64 МиБ). Загрузка допускается в свободный проект, только с непосредственным именем `.step`, `.stp` или `.ply`, и не заменяет существующий файл.

`import_project_scan` обрабатывает помещённый в проект PLY в редактируемую треугольную сетку и сохраняет имя/хеш источника, чтобы последующие изменения параметров заново обрабатывали именно исходный файл. Локальный MCP-адаптер предоставляет загрузку STEP и PLY через `cadyx_upload_project_step` и `cadyx_upload_project_scan`: оба читают локальный обычный файл и передают его байты, а HTTP-хост не раскрывает произвольные пути клиента.

Для временных референсов реконструкции `DELETE /api/v1/agent/projects/{id}/files/{name}` удаляет только непосредственный STEP из свободного проекта и отказывается это делать, пока актуальный `import_step` продолжает использовать файл. MCP-команда `cadyx_remove_staged_step` удаляет референс лишь после удаления тела; исходный локальный файл не меняется.

`POST /api/v1/agent/projects/{id}/copy-files` рекурсивно копирует пользовательские файлы из другого свободного проекта, исключая метаданные и runtime-состояние `.cadyx-*`; сначала проверяются конфликты, перезапись запрещена. MCP-эквивалент — `cadyx_copy_project_files`. `POST /api/v1/agent/projects/{id}/prune-files` рекурсивно удаляет пользовательские файлы, сохраняя указанные прямые имена. Он требует свободный проект с пустым документом, сохраняет метаданные проекта и `.cadyx-*`, сообщает хеши оставшихся файлов. MCP-эквивалент — `cadyx_prune_project_files`. К файловым маршрутам применяется политика аутентификации хоста.

`POST /api/v1/agent/projects` принимает `select: false`, чтобы создать проект, не меняя выбор браузера, например, для загрузки файла, пока агент работает с другим проектом.

## Политики доступности проекта

`CadyxCore._project_availability` объединяет снимок блокировки и состояние выполняющейся операции. Сохранённая активность dashboard остаётся отдельным сигналом для интерфейса/отчётов, но не участвует в допуске команды Core. Политика доступности — единая граница Core для чтения и записи проекта, управления файлами, выбора ресурсов и деструктивных операций. Отсутствующая, занятая или неизвестная блокировка не считается свободной.

Read-only-инспекция и списки используют неблокирующий снимок lease и возвращают последний атомарно сохранённый проект, даже пока работает писатель. Новую блокировку на изменение можно получить лишь для свободного проекта без требования восстановления и без выполняющейся операции; команда всё равно должна получить допустимую блокировку владельца и ревизию. Уже принятая к исполнению с корректной блокировкой команда остаётся атомарной, даже если блокировка истечёт во время работы.

Управление файлами и разрушительные действия требуют `FREE`, отсутствия восстановления блокировки и активной операции; в противном случае сохраняются существующие ошибки `PROJECT_BUSY` или `PROJECT_LOCKED`.

Выбор workspace — подсказка процессу браузера, а не способ определить владельца или направить команду. Core проверяет только целевой проект: он должен быть `FREE`, без требования восстановления и выполняющихся операций; можно выбрать проект с незавершённым workflow, если в данный момент между командами. Разрешено переключиться с занятого текущего проекта и выбрать проект, пока у других выполняются workflows. Создание проекта с выбором не ждёт workflows остальных проектов; `select: false` сохраняет текущий выбор. Разные чаты должны явно передавать `project_id` при операциях с проектом. Только отдельная блокировка проекта предотвращает одновременное редактирование двумя сессиями.


## Блокировки на изменение

В боковой базе `.cadyx-leases.sqlite3` у каждого проекта хранится одна долговечная блокировка, общая для локальных процессов хоста, использующих один workspace. Запись содержит `project_id`, `owner_type`, `owner_id`, время получения и heartbeat, непрозрачный `lease_id` и тайм-аут, выбранный при получении. Типы владельца: `agent`, `human`, `system`; состояния включают `FREE`, `AI_LOCKED`, `HUMAN_LOCKED`, `SYSTEM_LOCKED`. Heartbeat с хоста, настроенного на иной тайм-аут, не меняет исходный срок блокировки.

Все записи документа проходят через `CadyxCore.execute_command` и требуют текущий ID блокировки с подходящим для данного API владельцем-человеком или агентом. Транзакция SQLite `BEGIN IMMEDIATE` удерживает межпроцессную блокировку ОС проекта на время проверки lease, загрузки документа, выполнения команды, проверки и атомарной замены `project.json`. Получение, heartbeat, освобождение, инспекция и восстановление используют ту же блокировку. У разных проектов отдельные базы, они остаются независимыми.

Если занятый проект не освободился за пять секунд ожидания, операция возвращает `PROJECT_BUSY` (HTTP 409). Её можно повторить; текущую команду не прерывают.

Истечение heartbeat помечает блокировку устаревшей, но не освобождает проект автоматически. Для восстановления Core получает ту же блокировку, загружает последний атомарно сохранённый проект, проверяет документ и геометрию и лишь затем удаляет просроченную запись. Команда, начатая с корректной блокировкой, может завершиться после её истечения; восстановление не пересечётся с сохранением.

При аварийном завершении процесса блокировка SQLite снимается, но зафиксированный lease сохраняется, в том числе после перезапуска сервера. После истечения срока всё равно требуется процедура восстановления. Сбой до атомарной замены оставляет прежнюю ревизию; сбой после — полный новый документ и историю. Клиент мог не получить ответ, поэтому перед повторным запуском команды после потери связи проверьте сохранённую историю.

Механизм рассчитан на взаимодействующие актуальные хосты CADYX на одной локальной машине и локальной файловой системе. Перед обновлением остановите старые хосты: прежние версии не поддерживают текущий протокол остановки агента, а самые ранние не имеют общих межпроцессных блокировок. Не удаляйте и не заменяйте базы координации или журналы при работающих хостах. Резервное копирование/перенос выполняйте при остановленных хостах; боковые файлы координации — отдельные runtime-данные, не часть переносимого `project.json`. Прямая запись сторонними процессами и сетевые файловые системы вне контракта.

Доставка SSE ограничена процессом. Лёгкий периодический опрос обновлений браузером автоматически показывает подтверждённые изменения проекта и файлов workspace, внесённые другим взаимодействующим хостом.

## Безопасная остановка и возобновление агента

Внешний агент вызывает `POST /api/v1/agent/projects/{id}/stop`, передавая `lease_id`. Сначала Core фиксирует ограждение для токена в `.cadyx-agent.sqlite3` независимо от транзакции документа/блокировки. Команда проходит в исполнение, когда под защитой проекта проверяет это ограждение: команды, допущенные до его установки, могут завершиться; последующие команды с тем же токеном получают `AGENT_STOPPING`.

Затем stop получает ту же блокировку проекта, проверяет, что этот токен владеет текущей агентской блокировкой, заново загружает и проверяет сохранённый документ и геометрию и освобождает блокировку. Это позволяет безопасно остановить и просроченную блокировку агента. Запрос stop со старым токеном не может снять человеческую блокировку либо блокировку нового владельца. Команды принудительно не прерываются.

Успешный ответ содержит `stopped: true`, `project`, `document`, `history` и ставшую свободной блокировку `lock`; ревизия и история отражают последнюю целиком атомарно сохранённую версию. При ошибке проверки блокировка и долговечное ограждение сохраняются. Для занятого проекта через пять секунд может вернуться `PROJECT_BUSY`, при этом ограждение остаётся активным; повторите stop с тем же токеном. При сбое хоста ограждение сохраняется. Если ответ на stop потерян, проинспектируйте проект: свободная блокировка либо блокировка нового владельца означает, что прежний токен уже не владелец. Повтор stop не снимет блокировку нового владельца. Восстановление истёкшей блокировки остаётся доступным и также проверяет сохранённое состояние.

Чтобы продолжить работу (или начать её с защитой ревизии), проинспектируйте проект и вызовите `POST /api/v1/agent/projects/{id}/resume`, передав `owner_id` и целочисленную `expected_revision`. Внутри одной блокировки проекта Core проверяет сохранённое состояние, сверяет ревизию, получает новую агентскую блокировку и возвращает `resumed: true`, `lease` и полный снимок инспекции. Активную блокировку нельзя отобрать; сначала требуется остановить/восстановить истёкшую. Если человек отредактировал модель после инспекции, возвращается `REVISION_CONFLICT`: повторно инспектируйте проект и пересмотрите следующую команду. Resume не выполняет команды и не восстанавливает прежний снимок модели.

Каждая команда на возобновлённой блокировке требует `expected_revision`. При отсутствии/недопустимом значении возвращается `VALIDATION_ERROR`, при изменившейся ревизии — `REVISION_CONFLICT` до исполнения. После каждого успешного ответа обновляйте ожидаемую ревизию. Если ответ команды потерян, перед повтором проверьте ревизию и сохранённую историю, чтобы установить, зафиксировалась ли команда; автоматически повторять её нельзя. Повтор с той же ожидаемой ревизией не может создать второе успешное сохранение.

Существующие операции получения блокировки `/leases` и выполнения команд остаются совместимыми: для таких lease `expected_revision` необязательна и наличие поля не обязательно проверяется. Новым агентам для защищённой работы следует использовать `/resume`.

Служебная SQLite-база хранит только ограждения токенов и флаги защиты ревизий; новая возобновлённая блокировка очищает предыдущие токены. Переносимую схему проекта/документа это не меняет, миграция формата не нужна. Пока хосты работают, сохраняйте обе SQLite-базы координации. UI-кнопки остановки находятся вне этого этапа API.

## Agent Runtime

`cadyx.agent_runtime.AgentRuntime` выполняет для одного существующего проекта цикл вызова провайдера и инструментов, независимый от поставщика модели. Адаптер реализует небольшой протокол `AgentProvider.complete(messages, tools)` и преобразует нативные форматы запроса/ответа в типы CADYX `AgentMessage`, `AgentToolSpec`, `AgentResponse`. В Core нет SDK провайдера и настроек под конкретного поставщика.

Среда предоставляет провайдеру три инструмента: инспекцию текущего проекта, чтение сцены viewport и исполнение одной команды Command System. Для каждой команды Runtime получает новую агентскую блокировку, проверяет последнюю осмотренную ревизию, поддерживает heartbeat только во время команды и в `finally` освобождает блокировку проверенной остановкой агента.

Во время ожидания провайдера и read-only-инструментов блокировка не удерживается; явная инспекция обновляет ожидаемую ревизию. Конкурирующий редактор или изменение ревизии возвращает структурированный конфликт и не освобождает чужую блокировку. Число раундов вызова инструментов и их суммарное количество ограничены.

Неожиданная ошибка команды/очистки сохраняет исходную ошибку и запускает попытку проверенно освободить блокировку. При ошибке только провайдера освобождать нечего.

Runtime — внутрипроцессный Python API `cadyx.AgentRuntime`, а не интеграция с конкретным провайдером, HTTP-маршрут или фоновая служба. До запуска Runtime проект создаётся существующим Core или Agent API. См. [модуль Agent Runtime](../../cadyx/agent_runtime.py) и [целевые тесты](../../tests/test_agent_runtime.py).

## Механизм саморазвития возможностей

Провайдеронезависимый Agent Runtime и локальная MCP-поверхность распознают неизвестную команду Command System и возвращают `CAPABILITY_MISSING`. Агент может проверить постоянный реестр возможностей workspace, предложить новую возможность, выполнить её в изолированном `Document` с активным геометрическим ядром, зарегистрировать успешный результат, запустить способность в целевой модели и при необходимости восстановить предыдущую контрольную точку реестра.

Операции доступны в Agent API по `/api/v1/agent/projects/{id}/capabilities`; контракты команд и зарегистрированные способности возвращаются через `GET /api/v1/agent/capabilities`.

Реестр находится в корне workspace: `.cadyx-capabilities.sqlite3`. Запись возможности включает постоянный ID, заголовок и описание, версию MAJOR.MINOR.PATCH, закрытые схемы входа/выхода, привязки полей к результатам команд, зависимости, декларативные шаги Command System, тестовые данные/доказательства, хеш актуального контракта команды и имя вызова MCP. Перед заменой способности снимаются контрольные точки SQLite; `cadyx_rollback_capability` возвращает предыдущую версию. Для повторного использования доступны только совместимые записи в состоянии `ready`.

Каждая живая команда внутри способности отдельно получает и освобождает блокировку агента с защитой ревизии. Поэтому завершённые шаги остаются сохранёнными и видимыми, если следующий шаг завершится ошибкой.

Инструкции модельного агента по умолчанию сначала предлагают испытанную композицию. Если алгоритму не хватает кода, вместо неё используется ограниченный путь разработки исходников. Агент может читать только разрешённые `cadyx/*.py`, `tests/test_*.py` и Markdown-файлы. Предложение привязано к ревизии через SHA-256 каждого файла; ограничения: не более 12 файлов, 256 КиБ на файл, 2 МиБ суммарно и восемь уже существующих модулей `tests.test_*`. Нельзя добавлять зависимости, менять runtime/нативные бинарные файлы, данные проектов или конфигурацию.

Кандидатные файлы и выбранные тесты копируются во временное дерево. В Windows изолированный интерпретатор Python запускается через `CreateProcessW` с `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` в одноразовом именованном AppContainer без сетевых возможностей. CADYX выдаёт SID пакета только чтение каталогов кандидата и среды, а единственной папкой для записи задаёт профильный `Temp` AppContainer. После завершения процесса временные разрешения ACL и профиль удаляются.

Через явный список дескрипторов процесс наследует только дескриптор файла диагностики с правом записи. Для него создаётся Job Object на один процесс; лимит времени — 180 секунд, памяти — 2 ГиБ. Окружение разрешает только стандартные переменные среды Windows. Временные папки Python наследуют ACL профиля AppContainer, поэтому вложенные тесты могут создавать scratch-файлы, не получая доступа к кандидатным исходникам.

Если создание AppContainer, настройка ACL, ограничения процесса или очистка не прошли, операция закрывается с ошибкой `SOURCE_SANDBOX_UNAVAILABLE`; кандидат никогда не запускается в обычном режиме. Регрессионная проверка безопасности Windows удостоверяет, что запись временных scratch-файлов работает, но sentinel хоста нельзя читать/менять и исходящие сетевые подключения не проходят.

Только после того, как как минимум один выбранный тест завершится успешно без ошибок и падений, CADYX сохраняет долговечную контрольную точку в `.cadyx-source-extensions.sqlite3` и атомарно применяет патч, сверяя исходные хеши. Ошибка при частичном применении откатывает изменения. Откат восстанавливает файлы только если текущий хеш каждого совпадает с хешем применённой версии; изменения человека приводят к `SOURCE_REVISION_CONFLICT`.

Agent API предоставляет чтение, список, разработку и откат по `/api/v1/agent/projects/{id}/source-extensions` и `/api/v1/agent/source-files/read`; Agent Runtime и локальный MCP дают соответствующие инструменты. Успешная установка исходников через HTTP назначает управляемый перезапуск хоста после возврата результата. Модель проекта сохраняется и доступна для инспекции после перезапуска.

Это ограниченный путь обновления доверенных исходников, а не произвольный процесс или shell. Изменения, которым нужна новая внешняя зависимость или нативная библиотека, находятся вне его области.

Этапы жизненного цикла возможностей используют существующий поток SSE `agent.activity`. Браузер получает обновления разработки через тот же поток: название операции, результат тестов и итог интеграции. Текущие версии исходных расширений и статус их жизненного цикла сохраняются при перезапуске хоста.

Тесты: [саморазвивающиеся возможности](../../tests/test_self_evolving.py), [жизненный цикл Agent Runtime](../../tests/test_agent_runtime.py), [Agent API](../../tests/test_web_api.py).

### Профиль внутренней эвольвентной шестерни

`add_sketch_internal_involute_gear` создаёт замкнутую границу внутреннего зубчатого венца как редактируемый замкнутый периодический сплайн эскиза XY через вычисленные точки. В `gear_parameters` возвращаются модуль, число зубьев, угол давления, центр, поворот и боковой зазор.

Для внешней и внутренней шестерни при выдавливании границы рёбер OCCT используют периодические B-spline, проходящие через те же точки. Эскиз хранит один замкнутый сплайн и исходные точки, не цепочку отрезков; изменение параметров заново генерирует сплайн, а старые эскизы из линий преобразуются при следующем параметрическом перестроении.

Команда требует существующую внешнюю окружность и отсутствие других профилей в эскизе, чтобы `extrude_sketch` мог сохранить кольцо как один внешний контур и один внутренний зубчатый. Используются стандартные радиусы внутренней шестерни без смещения исходного профиля: `pitch = module * teeth / 2`, `tip = pitch - module`, `root = pitch + 1.25 * module`. Контрольные точки строятся по математической эвольвенте боковой поверхности зуба и окружным сегментам вершин/оснований.

Ребро OCCT — периодический интерполяционный B-spline через эти точки, не точная аналитическая эвольвента и не аппроксимация с сертифицированной точностью. Применяется та же проверка минимального числа зубьев против подрезания, что и для внешнего генератора. Выдавливание создаёт проверенную редактируемую B-rep OCCT с полостью по периодическому B-spline.

### Кинематика планетарного редуктора и движение в viewport

Read-only-маршрут `POST /api/v1/agent/projects/{id}/validations/planetary-kinematics` читает метаданные построенных внешних/внутренних шестерён на точной сохранённой ревизии. Проверяются соответствие модуля и угла давления, равенство числа зубьев планет, делительные межосевые расстояния солнце–планета и венец–планета, индексация равномерно расставленных зубьев и сохранённые фазы обоих зацеплений.

Идеальный решатель скоростей жёстких тел использует условия индексации планет `(Ns + Nr) * planet_spacing / 360 = integer` и скорость водила `wc = (Ns*ws + Nr*wr) / (Ns + Nr)`. Результат сообщает вращение планет, делительные межосевые расстояния, невязки фаз и равномерность расстановки планет. Это проверка идеальных кинематических связей; она не моделирует упругий контакт, нагруженный люфт, баланс сил или производственные допуски.

Необязательный `animate_duration_ms` отправляет событие `viewport.body-motion` выбранному браузерному viewer. На ограниченное время анимируются вращение/орбита существующих сохранённых B-rep тел по траекториям решателя; после завершения восстанавливаются сохранённые положения. Геометрия и ревизия документа не меняются, постоянная запись сопряжения сборки не создаётся. Для анимации сохранённого водила с рассчитанной скоростью задайте `carrier_body_id`. Контракт операции и локальная MCP-команда генерируются из `cadyx/api_contracts.py`.

## Команды и геометрия

Многоконтурное выдавливание линейных контуров добавляет каждый контур отверстия внутренним проволочным контуром той же грани OCCT перед одной операцией prism. Для криволинейных или аналитических сегментов остаётся существующий проверенный путь последовательных булевых операций. В обоих случаях исходные редактируемые контуры сохраняются и используются при перестроении.

Общая Command System поддерживает коробки и изменение параметров; импорт сканов PLY из workspace/проекта и изменение параметров; постоянный импорт загруженного PLY только с точками; импорт одного прямого STEP-тела; эскизы XY/XZ/YZ/CUSTOM/FACE с ограничениями; замену профиля/траектории; связанные элементы твёрдых тел.

Импорт только с точками сохраняется как постоянное облако без граней и не может использоваться как треугольная сетка для извлечения сечений скана. Выдавливание/вращение профиля, sweep круглого сечения, объединение связанных булевых тел и скругление рёбер по топологии создают редактируемые B-rep OCCT.

Импорт STEP сохраняет переданную B-rep OCCT с хешем источника и метриками геометрии; если OCCT не может исправить исходную форму в документированном допуске, она остаётся помеченной как некорректная. Дескрипторы элементов хранят исходные эскизы или тела и параметры; поддерживаемые изменения выше по цепочке перестраивают зависимые элементы по порядку документа в одной атомарной команде.

Булево объединение принимает пересекающиеся B-rep-тела, в том числе трубы sweep и результаты прежних fuse/fillet, и должно вернуть одно связное тело. Скругление выбирается по актуальным уникальным индексам рёбер B-rep из Agent topology API; индексы являются результатом текущего обхода топологии, а не постоянными именами.

Команды сканирования разрешают непосредственные PLY из workspace/проекта через `ProjectWorkspace`, выполняются с той же блокировкой Core и атомарным сохранением, никогда не меняя исходный файл. Каждая обработанная сетка публикуется рядом с источником как атомарный бинарный PLY с именем по содержимому; одинаковый файл переиспользуется, конфликтующие файлы не перезаписываются.

Элемент `reconstruct_scan` хранит путь и хеш источника, метаданные результирующего файла и параметры обработки. Геометрия тела `cadyx-mesh-v1` хранит в `project.json` ограниченные по размеру сжатые вершины float32 и грани uint32. Core сохраняет последние 128 снимков активности проекта в памяти и отправляет изменения по SSE `agent.activity`. Снимки охватывают инспекции Agent Runtime/API, запросы рендеринга, команды, твёрдотельные операции, повороты камеры и нативные этапы сканирования. Браузер показывает текущее действие/задачу и историю завершённых/ошибочных действий с временными отметками, новые сначала, не раскрывая полный журнал.

Протокол `GeometryKernel` отделяет Core CADYX от конкретного ядра. `OCCTKernelAdapter` создаёт/проверяет коробки, выдавливания и вращения профилей, трубы sweep, объединённые и скруглённые тела, а также импортированные STEP-тела; он также проверяет старые дескрипторы `primitive-v1`. Адаптер проверяет и триангулирует переносимые сетки, не преобразуя их в B-rep. `PrimitiveKernelAdapter` остаётся для демонстраций и B-rep не создаёт. Точные команды и ограничения см. в [контракте Document Model v7](document-model-v7.ru.md#эскизные-элементы-твёрдого-тела).
