# CADYX Codex rules

- Before any substantive work on CADYX—analysis, planning, code or documentation changes, reviews, recommendations, or commits—refresh project context from the current target branch/revision. Re-read `.codex/rules.md` and `.codex/memory.md`, inspect the files relevant to the task, and verify recent repository state/changes as needed. Treat prior-chat/model memory as potentially stale and never rely on it when the current repository state can be checked.
- The CADYX web panel targets desktop PCs exclusively. Review and verify its layout at desktop sizes; tablet and phone layouts are out of scope unless the user changes this requirement.
- Work directly on `main`. Do not create feature, staging, temporary, or work branches unless the user explicitly changes this policy. CADYX should normally have exactly one branch: `main`. If an accidental branch is created, fast-forward/merge its work into `main` and remove the extra branch.
- When choosing or updating any dependency/runtime/tool version, use the newest stable release and verify it from its official source. Do not choose an older compatible release as a workaround: the user explicitly requires adapting or building the kernel when necessary. Never bypass dependency checks to claim compatibility. Reviewed versions and reproducible local setup live in `scripts/runtime-versions.json` and `scripts/setup-runtime.ps1`.
- When a task encounters a reproducible failure, investigate and fix its root cause instead of switching to a workaround that leaves the defect in code, runtime, or configuration. Use an alternative path only to diagnose the failure, then return to the original scenario and verify the fix. If a confirmed external constraint makes the cause impossible to fix, report the blocker rather than treating a workaround as completion.

- Keep CADYX AI-first: the browser is the user's visual observation surface, never the agent's control plane. All agent-initiated CADYX interaction, including selecting projects or folders, must use CADYX Core/Agent APIs and the Command System; never operate the browser UI or its DOM with mouse, keyboard, or scripts. User navigation among saved projects is read-only: Projects (07) can open any project through its explicit viewer URL regardless of locks, without changing process-local Agent API selection. Agent API selection changes remain subject to Core availability policy; workspace-folder selection remains Agent API-only. The Core owns authoritative project state.
- While a project is being edited, keep its mutation controls disabled. Project-list navigation and read-only project inspection/rendering remain available for busy projects and use the atomically saved snapshot. Editing and other project mutations are enabled only after the API confirms the selected project lock is FREE and its activity snapshot has no running operation; unknown or stale availability remains locked.
- Use this repeatable API workflow for new CAD models: create the project through `POST /api/v1/agent/projects` so `project.created` selects it in the live viewer. For each mutation, read the current revision, acquire an agent lease immediately before the command, pass `expected_revision`, and release the lease immediately afterward; do not hold it while reasoning, inspecting, or waiting. For a genuinely long-running operation, use `AgentRuntime` or an independent heartbeat worker for the entire operation. Keep edits as separate committed commands so the viewer animates each operation event. Inspect the final document, scene, rendered image from useful angles, dimensions, datum, profile closure, intersections, and B-rep topology without an edit lease; after the final check confirm `FREE`. Use lease recovery only after an API check confirms expiration, never as normal control flow. Keep project-specific names, IDs, dimensions, and command transcripts in the CADYX project/history; keep management documentation limited to reusable workflow and confirmed capability guidance.
- Use clear, human-readable names for projects, bodies, sketches, features, and user-facing files. Project display titles may use the user's language; `/p/<project-slug>` addresses must use a separate lowercase English `url_slug` made of ASCII letters, digits, and hyphens. When creating or renaming a project with a non-English title, supply an English URL slug with the Agent API. Include numbers in display names only when they communicate design information such as a quantity or dimension (for example, `10 ячеек` or `3 мм`). Do not put opaque IDs, hashes, timestamps, revision codes, random suffixes, or other generated noise in display names. Keep system-required identifiers in metadata or technically required export filename suffixes, not in the model's display names.
- For a single-part model, name the project and final body after the part; do not call it an assembly unless it contains an actual assembly structure. Keep a result body's name descriptive of the whole part, never the last operation (such as a chamfer or fillet). Preserve operation-specific names in feature records only when the document stores them separately; when a command's `name` field sets the result body label, pass the part name or rename the final body before completion. Verify the visible project and final-body names in the saved document.
- Before the first model mutation for any modeling request, inspect the target project and its references, then prepare a concrete ordered plan of 3–7 phases. Each phase must describe a meaningful, observable result specific to the requested model; include geometry creation and final validation, and avoid generic filler or invented tasks. Publish the plan to `POST /api/v1/agent/projects/{id}/dashboard` before executing any model command, with `progress_percent: 0`, the ordered phases initially `pending`, and an honest `eta_seconds` estimate or `null`. Write dashboard workflow titles, phase names, task titles, and agent activity actions in Russian. Keep object and file names supplied by the user or source files unchanged. Project display titles may remain in the user's language; use an English `url_slug` for the project address. Send `tasks: []` unless there are actual queued tasks. After work starts, update the same report at meaningful phase transitions with accurate states, progress and ETA; if the plan changes, publish the revised plan before continuing. Mark phases complete only after their outcomes are verified, and report failures as `failed`. Never fabricate progress, ETA, task-queue entries, or hardware telemetry. If a required modeling decision is missing, publish the known plan and request that decision before making the dependent mutation. The report does not require an edit lease; its schema and lifecycle are documented in [viewport API](docs/viewport-api.md#agent-dashboard-reports).
- If a required CAD operation is missing or incorrect, identify the capability gap and inspect the existing architecture before changing the model. Implement the capability as a reusable CADYX feature across every affected layer: geometry kernel, parametric model and persistence, Core/Command System, Agent API and MCP, and web viewport. Add and run automated tests for the new behavior. Then resume the original modeling request using the implemented capability, and complete and inspect the requested model. Do not substitute approximate geometry, temporary stubs, skipped operations, or one-off workarounds; do not weaken or change the requested outcome to avoid implementation. Report completion only after the capability and final model have been verified. Report a blocker only when a real project or environment constraint prevents implementation, with the specific constraint and evidence.
- Build final models from editable sketches and solid features whenever the geometry can be authored that way. Give each model's primary user-adjustable dimensions named feature parameters, show current dimensions and inputs in Geometry as the model is built, and verify edits rebuild the B-rep. Do not leave an imported or rigidly transformed B-rep as the only final model when a source sketch or design feature can describe it.
- Treat a small, design-preserving feature tree as a standing requirement for every model. Before construction, identify repeated locations and compatible geometry, then plan the fewest standard parametric features that preserve intent, editable dimensions, and rebuild robustness. Prefer one multi-position hole, patterned feature, multi-profile operation, or multi-edge finishing operation over repeated single-position commands when the features share their functional purpose and controlling dimensions. Batch compatible fillet/chamfer edges from the same pre-feature body. For each sketch-driven solid feature, create a dedicated source sketch and preserve its explicit sketch-to-feature lineage; operations that require multiple profiles, such as lofts, may use their required set of section sketches. Do not reuse a source sketch across separate solid features. Body-topology operations such as fillets and chamfers do not need fabricated sketches. Put coplanar through-hole contours that share a depth in the base profile; use a sketch pattern for repeated identical holes when available, instead of issuing one 3D hole command per location. For plate-and-boss parts, prefer two profiles and two additive operations (base extrusion plus one fused boss pad), then only the required chamfer and spatial fillet. Use an annular boss profile to preserve its bore, and use `add_sketch_rounded_rectangle` or profile arcs for planar corner rounds. Keep a true 3D root blend as a fillet feature when it cannot be represented faithfully in the extrusion profile. `extrude_sketch` and `pad_sketch_to_body` accept one outer loop with enclosed inner loops for holes; preserve those contours in the source sketch so a compact tree does not grow into repeated hole features. Keep sketch construction and viewport animations enabled while reducing redundant operations. After construction, audit the whole feature tree for repeated compatible operations and simplify them before final validation. If CADYX lacks a suitable batch/pattern operation, check for an existing parametric alternative and implement the smallest reusable capability when the repeated geometry is important to the model.
- When retiring an existing feature chain after its replacement is verified, collect all obsolete body, feature, sketch, and sketch-element IDs and remove them with one `remove_objects` command. Keep retained objects outside the removal set; any reference from retained objects rejects the whole command. Use individual `remove_body` only for an isolated body.
- Do not impose a fixed count ceiling on sketches or feature operations in a model. Remove arbitrary per-command count ceilings that prevent a model from using its full sketch or feature history, and keep algorithms scalable as those collections grow.
- User decision: the 357-item sketch-tools list in [the backlog](../docs/sketch-tools-backlog.md) is deferred; its pending rows are not an instruction to implement the entire list now. Avoid long one-by-one visible model runs and reserve broad visual/load verification for grouped or integration runs.
- Treat each reference-driven modeling or model-study task as both a geometry task and a CADYX improvement opportunity. While reconstructing or studying the reference, identify concrete gaps in CADYX's modeling workflow, commands, kernel, inspection, or visualization. Implement and verify improvements that are necessary or clearly in scope; record confirmed reusable capabilities and limitations in their canonical docs and `.codex/memory.md`. Keep one-off measurements, project IDs, source-specific geometry, and command transcripts in the CADYX project/history, not shared memory.
- For reference-driven solid modeling, implement the actual editable B-rep operations the geometry needs: a round tube along a smooth path must use a sweep, and rounded edges must use OCCT fillets selected from inspected B-rep topology. Do not substitute a flat extruded strap or a mesh-only visual approximation for these operations; record the exact command and topology contract in the canonical model documentation.
- Keep imported source/reference bodies hidden in the viewport during and after reconstruction. Retain them in the project only when needed for comparison or validation, and keep them available to those checks; the final visible scene should show the reconstructed model rather than its source mesh.
- Make agent work visually observable in the browser: animate each meaningful sketch edit, solid operation, camera change, model update, and failure as it happens. Keep the user's CADYX view on the target resource. During scanner work, show the current cloud in the CADYX viewport and refresh it after every captured frame, registration, cleanup/filter, and fusion update; label the frame angle/count and whether scale, registration, and cleanup are verified or provisional. Keep progress visible during long operations and do not leave the browser showing an older frame after a newer result is available. Select projects and workspace folders through the Agent API, which updates the passive viewer through SSE. Use real operation events, not a raw command or transcript feed. Keep the dashboard to one progress block showing current status, progress/ETA, the current or last actual agent action, its current or most recently finished task, and a compact history of completed/failed actions newest first with their completion times. Hide a repeated current-task row when it duplicates the current action. Keep the plan and future queue entries in the Agent API for the agent; do not show upcoming work in the browser. Do not invent missing plan, queue, or hardware telemetry data. Keep the full detailed activity journal available to agents through the API; the browser history is a concise action list, not a transcript. Show only the currently edited sketch as live geometry in the viewport. In the object tree, a referenced source sketch may appear as a nested, selectable child of its sketch-driven feature; selecting it highlights that sketch contour in the preview. Keep referenced sketches out of top-level rows, and do not show unrelated inactive sketches. A source sketch enters live viewport editing only while its profile is actively being edited; hide it as soon as that edit completes. Animate sketch strokes and profile feature formation smoothly rather than revealing the final geometry all at once. Implement required unsupported modeling operations as part of the requested scope; report a blocker only for a real project or environment constraint. Distinguish editable OCCT B-reps from triangle meshes.
- Before completing a goal that creates or changes a CAD model, inspect the final object as a whole, not only the validity of each operation in isolation. Verify the intended dimensions, datum/orientation, closed profiles, attachment/intersection or separation of parts, and final topology (for example, whether the requested product should be one fused solid or an assembly). Inspect the resulting API scene and a rendered viewport image from useful angles. A plausible preview or individually valid but unfused/intersecting bodies is not sufficient evidence that a single-part model is complete. Keep iterating on the geometry and, when needed, implement the missing CADYX capability before marking the goal complete.
- Store CADYX projects in human-readable, filesystem-safe directories derived from their display names, adding a suffix for collisions. Keep UUIDs as stable internal/API identities and resolve projects from their saved records; preserve and continue reading legacy UUID-named folders. Page reloads must restore the selected saved project and its last committed model. Listing and read-only inspection/rendering must not wait on the edit lease for an active write; use the atomically saved snapshot so visual progress resumes after each committed operation.
- Do not mark a persistent goal complete merely because implementation steps succeeded or the session is about to end. Complete it only after every explicit user outcome, final-model review, and required project checks are finished; otherwise keep the goal active with enough concrete state to resume.
- Unless a modeling request specifies a different datum, start new model geometry at global Z=0 and use global Z as the vertical axis. Keep the viewport coordinate triad visible, allow camera orbit to reach the exact top view, and show the actual Z rotation axis on revolved bodies.
- If visible revolved bodies share an axis, orbit the camera around that axis at the model's Z midpoint and fit the full scene bounds relative to that pivot. Asymmetric attachments such as mug handles must not shift the camera pivot away from the revolution centerline.
- Project-local MCP servers, skills, plugins, or similar agent tooling may be created when they materially improve Codex's ability to build models. This is authorized by the user; do not add them proactively, only when a concrete task needs them.
- Keep generated scan-processing outputs in the same workspace folder as their source scans. Preserve imported sources and never replace them.
- In reference-driven reconstruction, use a staged STEP only while inspecting/building the new model. After verifying the new model, remove its unreferenced imported reference body with `remove_body` and `remove_source_file: true`; keep the user's original source file unchanged. Do not remove STEP files that remain dependencies of imported bodies.
- Manage the Windows host through `scripts/manage-host-task.ps1` from PowerShell (for example, `-Action Restart`); use the browser only to observe the host, never to control its lifecycle.
- Every document mutation must hold the project's current edit lease. AI and human must never edit the same project concurrently.
- When resuming interrupted model work, inspect the target project's lease before inspecting or editing it. If an agent lease is expired, use the validated `/leases/recover` API and wait for `FREE` before rendering or continuing; release the live agent lease after the final command and verification, then confirm the project is `FREE` before completing the goal.
- Treat `projects/` as user workspace data. Do not overwrite or delete imported CAD files, scans, meshes, images, measurements, or references during routine work.
- Keep geometry-kernel-specific APIs behind the `GeometryKernel` boundary; do not represent the demo primitive adapter as a production CAD kernel.
- Prefer existing mechanisms and avoid dependencies with only marginal benefit. Standing user authorization: add a mature third-party dependency when it provides a concrete improvement to performance, correctness, maintainability, or UX; no separate approval is needed for each such dependency. Keep the choice scoped, record why it helps, and update dependency manifests/lockfiles as required.
- Before every commit, review `.codex/memory.md` against the confirmed current project state: add useful durable facts, update changed facts, and remove stale ones. Keep canonical details in project documentation or code instead of duplicating them in memory.
- Cross-PC workflow: after each completed task that changes project source, configuration, tools, documentation, or reusable source fixtures, make one task-only commit and push it to `origin/main` by default. The user has authorized this as the standing CADYX workflow; follow a later explicit instruction to keep a change local. Keep `projects/` as local user workspace data: never include its contents in commits or pushes, and stage task files by explicit path rather than broad-add commands.
- Before pushing, fetch `main` and compare it with local `HEAD`. If remote `main` has advanced, pull and merge those commits locally, resolve and verify the merge, then push. Do not push while local `main` is behind its remote.
