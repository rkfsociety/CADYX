# CADYX Codex rules

- Before any substantive work on CADYX—analysis, planning, code or documentation changes, reviews, recommendations, or commits—refresh project context from the current target branch/revision. Re-read `.codex/rules.md` and `.codex/memory.md`, inspect the files relevant to the task, and verify recent repository state/changes as needed. Treat prior-chat/model memory as potentially stale and never rely on it when the current repository state can be checked.
- Work directly on `main`. Do not create feature, staging, temporary, or work branches unless the user explicitly changes this policy. CADYX should normally have exactly one branch: `main`. If an accidental branch is created, fast-forward/merge its work into `main` and remove the extra branch.
- When choosing or updating any dependency/runtime/tool version, use the newest stable release and verify it from its official source. Do not choose an older compatible release as a workaround: the user explicitly requires adapting or building the kernel when necessary. Never bypass dependency checks to claim compatibility. Reviewed versions and reproducible local setup live in `scripts/runtime-versions.json` and `scripts/setup-runtime.ps1`.

- Keep CADYX AI-first: the browser is the user's visual observation surface, not the agent's control plane. Codex operates projects and models under the hood through the Core/Agent API, Command System, and other tools. The user observes the work and may orbit the viewport camera; add other user-operated modeling controls only when requested. The Core owns authoritative project state.
- Make agent work visually observable in the browser: animate each meaningful sketch edit, solid operation, camera change, model update, and failure as it happens. Keep the user's CADYX view on the target project. Operate the product under the hood through Core/Agent APIs; do not control its web panel with virtual mouse or keyboard. Use real operation events, not a raw command or transcript feed. The activity card contains only the fixed label `РАБОТА АГЕНТА` and one status line: the current action, a brief `· готово`/`· ошибка` result, or `Думает` when idle. Do not show stages, source/output details, or a user-facing history; keep the detailed activity journal available to agents through the API. Show only the currently edited, unused sketch in the viewport and object tree. Hide every inactive sketch and every sketch already referenced by a solid feature. After an operation uses a sketch, remove its visible overlay immediately. Animate sketch strokes and profile feature formation smoothly rather than revealing the final geometry all at once. If an operation is unsupported, implement the missing capability when it is within the task; otherwise show the real failure and describe the limit. Distinguish editable OCCT B-reps from triangle meshes.
- Unless a modeling request specifies a different datum, start new model geometry at global Z=0 and use global Z as the vertical axis. Keep the viewport coordinate triad visible, allow camera orbit to reach the exact top view, and show the actual Z rotation axis on revolved bodies.
- Project-local MCP servers, skills, plugins, or similar agent tooling may be created when they materially improve Codex's ability to build models. This is authorized by the user; do not add them proactively, only when a concrete task needs them.
- Keep generated scan-processing outputs in the same workspace folder as their source scans. Preserve imported sources and never replace them.
- Manage the Windows host through `scripts/manage-host-task.ps1` from PowerShell (for example, `-Action Restart`); use the browser only to observe the host, never to control its lifecycle.
- Every document mutation must hold the project's current edit lease. AI and human must never edit the same project concurrently.
- Treat `projects/` as user workspace data. Do not overwrite or delete imported CAD files, scans, meshes, images, measurements, or references during routine work.
- Keep geometry-kernel-specific APIs behind the `GeometryKernel` boundary; do not represent the demo primitive adapter as a production CAD kernel.
- Prefer existing mechanisms and avoid dependencies with only marginal benefit. Standing user authorization: add a mature third-party dependency when it provides a concrete improvement to performance, correctness, maintainability, or UX; no separate approval is needed for each such dependency. Keep the choice scoped, record why it helps, and update dependency manifests/lockfiles as required.
- Before every commit, review `.codex/memory.md` against the confirmed current project state: add useful durable facts, update changed facts, and remove stale ones. Keep canonical details in project documentation or code instead of duplicating them in memory.
- Before pushing, fetch `main` and compare it with local `HEAD`. If remote `main` has advanced, pull and merge those commits locally, resolve and verify the merge, then push. Do not push while local `main` is behind its remote.
