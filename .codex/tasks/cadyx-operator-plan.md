# CADYX Operator: моделирование с развитием приложения

Статус: реализация завершена; приёмка из нового чата Codex ожидает ручного выполнения.
Дата: 2026-10-15.

## Цель и ожидаемое поведение

После выбора репозитория CADYX в Codex пользователь может попросить «создай модель стола», «исправь эту модель, добавь ручку» или «сделай модель по скану». Агент получает контекст через API, строит и проверяет модель. Если необходимой возможности нет, самостоятельно дорабатывает CADYX, проверяет расширение, подключает его через API и продолжает исходную задачу до проверенного результата.

Уточнения допустимы для существенных требований к изделию: размеры, масштаб скана, назначение, допуски, неоднозначный целевой объект. Не нужно повторно спрашивать разрешение на необходимые связанные изменения кода, API, тестов и обоснованные зависимости в пределах действующих проектных правил. Неизвестный масштаб или точность нельзя заменять выдуманными значениями.

Все операции с документами, геометрией, выбором проекта и камерой выполняются через CADYX API. Редактирование исходников, сборка и управление локальным хостом выполняются инженерными инструментами; прямое редактирование project.json, обход Command System, управление браузером и внешнее CAD-приложение как обход API запрещены.

## Проверенная отправная точка

- [Правила](../rules.md) уже требуют API-only работу, реализацию недостающих возможностей, проверку итоговой детали и разрешают обоснованные зрелые зависимости. Повторно вводить эти разрешения не требуется.
- [HTTP API](../../cadyx/web.py), [Core](../../cadyx/core.py) и [Command System](../../cadyx/commands.py) уже обслуживают проекты, команды, leases, ревизии, topology, dashboard и viewport. Контракты: [архитектура](../docs/architecture.md), [модель документа](../docs/document-model-v3.md), [viewport](../docs/viewport-api.md).
- [AgentRuntime](../../cadyx/agent_runtime.py) — существующий provider-neutral цикл с heartbeat и ограничениями; он не равнозначен готовому подключению Codex к CADYX. Не создавать второй автономный LLM runtime ради этой интеграции.
- Scan-to-CAD сейчас получает triangle mesh из PLY; редактируемый инженерный B-rep по произвольному скану не следует считать готовой возможностью. См. контракт модели документа и [ScanProcessor](../../cadyx/scan.py).
- При подготовке плана в рабочем дереве имеются посторонние незакоммиченные изменения. Перед реализацией заново проверить состояние и актуальные контракты; настоящий план не подтверждает работоспособность этих изменений.

## Архитектура решения

1. Краткий корневой AGENTS.md — обязательный вход: чтение .codex, выбор процесса моделирования/разработки, ссылка на проектный skill и правила. Не копировать весь rules.md.
2. Репозиторный skill CADYX Operator — повторяемый процесс и ссылки на канонические контракты, а не отдельная база знаний или список захардкоженных команд.
3. Локальный MCP-адаптер — узкий интерфейс инструментов поверх существующего HTTP Agent API. Core остаётся источником состояния, Command System — единственным путём изменения документа.
4. Расширения CADYX — только по конкретным потребностям модели, с сохранением GeometryKernel, атомарности и совместимости данных.
5. Плагин — возможная последующая упаковка. Для первой рабочей интеграции не требуется.

Размещение skill и конфигурации MCP, транспорт и библиотеки выбрать на этапе реализации после проверки актуальной официальной документации Codex и существующих зависимостей. Не предполагать, что выбор папки в Codex автоматически устанавливает MCP или перезагружает его инструменты.

## Этапы реализации

### 1. Зафиксировать контракт оператора и точку входа

**Изменить:** создать или дополнить применимый AGENTS.md и репозиторный skill; при необходимости уточнить существующие правила без дублирования. Описать выбор активной модели по API, допустимые допущения, вопросы о результате, полномочия на связанные доработки и зависимости.

**Почему здесь:** инструкции должны работать в новом чате без истории переписки; skill должен подключаться по смыслу запроса на моделирование или изменение детали.

**Проверить:** новый чат в выбранном проекте распознаёт три исходных сценария, читает нужные источники и выбирает API-процесс без ручного вызова skill. Если API не сообщает выбранный объект, агент не выдумывает выделение; использует явный идентификатор либо задаёт предметное уточнение.

### 2. Обеспечить обнаружение возможностей API

**Изменить:** сопоставить реальные routes, команды, параметры, ограничения и ошибки. Проверить наличие машиночитаемого описания; если недостаточно — добавить read-only контракт обнаружения возможностей в существующий API. Конкретный endpoint определить при реализации. По возможности получать схемы из общего источника с валидацией команд, не вести параллельный ручной каталог.

**Почему здесь:** агент должен отличать неизвестную операцию, некорректные параметры, конфликт ревизии и ограничение ядра; новые функции должны становиться доступны без расхождения документации и инструментов.

**Проверить:** описание соответствует исполняемым командам; неизвестные операции и неправильные параметры дают структурированные ошибки. Не заявлять полный каталог схем, пока он не проверен на соответствие диспетчеру и валидаторам.

### 3. Подключить MCP поверх Agent API

**Изменить:** реализовать минимальный адаптер для health, контекста/выбора/создания проекта, чтения документа и файлов, возможностей, topology, viewport/PNG/камеры, dashboard, выполнения команд и существующего lease/stop/resume процесса. Имена инструментов и схемы определить по проверенным контрактам. Изображение должно быть доступно агенту для визуальной проверки, а не только возвращаться непросматриваемым URL.

Не предоставлять универсальный shell, произвольный HTTP proxy или запись файлов модели через MCP. Аутентификацию передавать из runtime-конфигурации без секретов в Git и логах. Существующие ошибки и revision возвращать без сокрытия.

Для каждой мутации читать актуальное состояние и передавать expected_revision; держать lease только во время операции. Для длинных операций обеспечить независимый heartbeat, проверенную отмену и освобождение lease. При конфликте перечитать состояние, не повторять запись вслепую. После потери ответа сверить revision/history и результат до повтора: не предполагать наличие idempotency в текущем API.

**Почему здесь:** Codex получает управляемый набор инструментов, не обходящий авторитетный хост и его защиту данных.

**Проверить:** временный workspace и реальный HTTP host; успешная команда, неверные параметры, занятый/истёкший lease, устаревшая revision, потеря соединения, ошибка ядра, остановка и отсутствие утечек секрета. Отдельно проверить подключение и фактический вызов из Codex. Инструкции установки должны обозначать требуемое обновление подключения/чата.

### 4. Реализовать единый цикл «модель → недостающая функция → модель»

**Изменить:** закрепить в skill следующий порядок:

1. Получить API-контекст, исходники/референсы, ограничения изделия и состояние lease; выбрать целевой проект без изменения пользовательских источников.
2. До первой мутации опубликовать через dashboard предметный план из 3–7 фаз на русском; отделить уточнения требований от самостоятельного выбора технического решения.
3. Использовать существующие команды. При недостатке установить точный пробел и воспроизвести его в изолированном workspace.
4. Добавить минимальную возможность в необходимые слои: kernel/Core/Command System/API, сериализацию/миграцию, визуализацию и обнаружение возможностей — только там, где этого требует изменение.
5. Выполнить релевантные проверки. При необходимости обновить runtime, безопасно перезапустить локальный хост штатным скриптом после освобождения leases и убедиться, что новые возможности реально доступны. Учесть активную работу других проектов; не обрывать её автоматически.
6. Перечитать проект и revision через API, актуализировать topology, продолжить построение и проверить исходное требование. Не завершать задачу только потому, что новая функция реализована.

Зависимости выбирать по действующим rules.md: доказанная необходимость, зрелость, актуальная stable-версия из официального источника, совместимость runtime, лицензия, воспроизводимость, обновление manifest/lock. Не добавлять сервисы, платные операции или передачу моделей наружу под видом обычной библиотеки.

**Проверить:** сценарий с намеренно отсутствующей необходимой операцией проходит весь цикл, включая доработку, API-вызов и завершение модели. Не использовать визуальную mesh-подмену вместо требуемого B-rep. Несвязанный рефакторинг и пользовательские изменения не попадают в task-only commit.

### 5. Обеспечить проверку результата и восстановление

**Изменить:** описать и при необходимости дополнить API-проверки размеров, datum, замкнутости профилей, присоединения деталей, количества solid, валидности B-rep и изображения с полезных ракурсов. Для scan-задач сохранять источники и явно различать mesh, восстановленный B-rep и измеренную точность. Для инженерных проверок использовать направление существующего roadmap, не строить второй validation framework.

Сохранять необходимое состояние незавершённой задачи: проект, revision, ссылки на источники, выполненные/оставшиеся фазы и подтверждённые ограничения. Геометрические операции и модельная история остаются в CADYX; незавершённая инженерная работа — в .codex/tasks. Не хранить там токены и reasoning. По возобновлении сверять запись с API, не доверять старым IDs топологии.

Не обещать undo/rollback истории, пока соответствующий контракт не проверен или реализован. Ошибка операции должна сохранять последний корректный документ. Завершение требует честного dashboard, освобождения lease и подтверждения FREE.

**Почему здесь:** рабочий инструмент должен проверять продукт целиком и безопасно продолжать после ошибки, изменения кода или перезапуска.

**Проверить:** сбой посередине моделирования и перезапуск хоста не повреждают источники и последний сохранённый документ; новый чат продолжает с фактической revision, без повторного создания уже существующих деталей.

### 6. Выполнить приёмку из нового чата Codex

Проводить на временных проектах и копиях тестовых источников, без изменения пользовательских моделей:

| Запрос | Доказательство результата |
|---|---|
| Создать стол с заданными размерами | Редактируемая геометрия, проверенные размеры/ориентация, понятный состав деталей, изображение через API |
| Добавить ручку к существующей модели | Верно определён объект, сохранены исходные части, проверены соединения либо предусмотренное разделение деталей |
| Создать модель по PLY-скану | Источник сохранён; масштаб и вид результата указаны; mesh не выдан за B-rep; точность заявлена только в измеренной области |
| Необходима новая CAD-операция | Реализация и тест расширения, доступность через API/MCP, продолжение исходного построения |
| Прерывание и продолжение | Восстановление через проверенный lease/revision процесс, без дублирования успешных команд |

Уточняющий вопрос об отсутствующем инженерном размере — допустимый исход. Вопрос о разрешении реализовать необходимую связанную функцию при имеющихся полномочиях — дефект процесса.

**Проверка по стоимости:** сначала схемы и targeted unit tests, затем затронутые API/kernel/runtime tests; интеграция на временном host; обязательная итоговая проверка подключения в Codex. Полную сборку/native rebuild запускать только при затронутом коде или runtime, объяснив необходимость. CI и push — по действующим полномочиям, этот план push не разрешает.

## Критерии завершения будущей реализации

- В новом чате проектные инструкции находят skill и подключённые API-инструменты без пересказа истории пользователем.
- Доступ к документу и его изменениям идёт исключительно через CADYX API; отсутствуют скрытые прямые записи или browser automation.
- Агент самостоятельно завершает связанный цикл развития приложения, а затем исходную модель; новые полномочия не объявляются безграничными.
- Ошибки, конфликты, долгие операции и восстановление проверены; исходники и посторонние изменения сохранены.
- Итоговая геометрия и заявленные свойства проверены, пользователь видит реальные операции и честный результат.
- Setup и контракты обновлены в канонических источниках; .codex содержит только полезные актуальные ссылки и решения. После выполнения удалить этот временный план, перенеся только долговечные сведения.

## Границы текущей задачи

Реализованы этапы 1–5 и покрытие адаптера/API тестами. Конфигурация проекта зарегистрирована и MCP протокол проверен с текущим host. Этап 6 требует нового чата Codex и проверки модельных сценариев на временных проектах; эта сессия не должна создавать отдельный чат без прямого запроса пользователя. Удалить этот временный план после завершения этой приёмки.
